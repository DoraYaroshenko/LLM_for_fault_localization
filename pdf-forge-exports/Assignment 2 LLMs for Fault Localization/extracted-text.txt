1. Overview 
In this assignment, you will conduct an empirical software engineering study on the use of large 
language models (LLMs) for fault localization in Python methods. 
You will build and evaluate an automated experimental pipeline that compares how well LLMs 
identify faulty lines in buggy Python methods under different information conditions. 
The assignment focuses on: 
● empirical software engineering 
● automated experimentation 
● software testing 
● spectrum-based fault localization 
● LLM evaluation 
● reproducibility engineering 
● experimental infrastructure validation 
You will: 
● construct a benchmark of buggy Python methods based on HumanEval-style tasks 
● generate buggy versions using mutation 
● execute tests 
● compute SBFL rankings using Tarantula (or other formulas) 
● compare at least two LLMs through OpenRouter 
● evaluate fault-localization accuracy 
● validate your own experimental infrastructure 
● build a reproducible artifact 
● present your work as a professional static HTML website

3. Research Questions 
Your work should address the following research questions. 
RQ1 — Baseline Fault Localization 
How well do LLMs localize faults when given only the buggy method and the intended behavior? 
RQ2 — Effect of Test Information 
Does providing passing and failing tests improve LLM fault-localization performance? 
RQ3 — Effect of SBFL Information 
Does providing a spectrum-based fault-localization ranking, such as Tarantula, improve LLM 
fault-localization performance? 
RQ4 — Combining Tests and SBFL 
Does combining test information with an SBFL ranking improve performance more than either 
source alone? 
RQ5 — Model Comparison 
Do different LLMs perform differently on the same fault-localization task?

3. Dataset Construction 
You must construct a benchmark based on HumanEval. Can also use more advanced sources 
and more complex methods.  
Your dataset must include at least: 
● 30 methods 
● a short natural-language specification for each method 
● At least 10 tests for each method 
● one buggy version of each method 
● a known ground-truth faulty line or small faulty region 
● evidence that the original version passes the tests 
1 

● evidence that the buggy version fails at least one test 
For each selected HumanEval method, you must create a buggy version. 
You may use: 
● manual mutation 
● automatic mutation 
● mutation-testing tools 
● scripts written by you 
● AI-assisted generation of mutants, with manual validation 
Examples of suitable mutations include: 
● replacing < with <= 
● replacing && with || 
● changing an arithmetic operator 
● changing a boundary condition 
● returning the wrong variable 
● deleting a condition 
● changing a constant 
● mishandling empty input 
● introducing an off-by-one error 
Each mutant must satisfy the following requirements: 
● the original method passes all the tests 
● the mutated method fails at least one test 
● the faulty line or region is known 
● the bug is reasonably localizable 
● the mutant is not equivalent to the original program 
● the method remains small enough to fit clearly in an LLM prompt 
Prefer mutants where at least one test passes and at least one test fails, because this makes 
the passing/failing distinction meaningful for fault localization.

3. LLM Evaluation Setup and Experimental Conditions 
3.1 LLM Evaluation Setup 
You must compare at least two LLMs. 
All LLM calls must be made through the OpenRouter API. 
2 

You should record:

● date of execution

The default requirement is one run per prompt. 
3.2 Experimental Conditions 
For each buggy method and each LLM, you must run four information conditions. 
Condition A — Code Only 
Input: 
● buggy method 
● intended behavior 
Condition B — Code + Tests 
Input: 
● buggy method 
● intended behavior 
● passing/failing tests 
Condition C — Code + SBFL 
Input: 
● buggy method 
● intended behavior 
● Tarantula ranking 
Condition D — Code + Tests + SBFL 
Input: 
● buggy method 
● intended behavior 
● tests 
● Tarantula ranking 
3 

With 30 methods, 2 models, and 4 conditions, the minimum experiment size is: 
30 methods × 2 models × 4 conditions = 240 LLM calls 
3.3 Prompting Requirements 
You should use a fixed prompt template for all models and all methods. 
The prompt should change only according to the information condition. 
The model should be asked to return structured output, preferably JSON. 
Example: 
{ 
"top_1_line": 12, 
"top_3_lines": [12, 14, 9], 
"faulty_region": "loop condition", 
"explanation": "The loop condition may terminate before the last candidate is checked." 
} 
The prompt should explicitly state: 
“Do not repair the program. Your task is only to identify the most likely faulty line or small faulty 
region.” 
You must save the raw model outputs, even when they are incorrect or malformed.

4. Spectrum-Based Fault Localization 
For each buggy method, you should run the tests and identify: 
● passing tests 
● failing tests 
● expected output 
● actual output, where relevant 
You should also collect coverage information and compute a Tarantula-style suspiciousness 
score for executable lines. 
For each line s: 
failed(s) = number of failing tests that execute s 
passed(s) = number of passing tests that execute s 
4 

total_failed = total number of failing tests 
total_passed = total number of passing tests 
Tarantula suspiciousness: 
suspiciousness(s) = use the Tarantula formula 
The minimum is to compute suspiciousness based on Tarntula. You can use additional SBFL 
suspiciousness formulas.  
The LLM should receive only the ranking, not the ground-truth faulty line.
